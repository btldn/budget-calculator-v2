# ТЗ: приложение для семейного бюджета на двоих

Ты — ведущий разработчик этого проекта. Ниже полное описание продукта. Прочитай целиком, задай уточняющие вопросы, если что-то противоречит друг другу, и **предложи план по этапам до того, как писать код**. Каждый этап — рабочее приложение, которое можно запустить и потрогать, а не полуфабрикат.

---

## 1. Что это и для кого

Веб-приложение для учёта личных финансов **двух человек, живущих вместе**. Не SaaS, не мультитенант, не продукт для рынка. Ровно два аккаунта, оба доверенные, оба видят все данные. Разворачивается на своём VPS в докере.

Задача продукта: заменить общую Excel-таблицу так, чтобы ей действительно пользовались каждый день. Значит, ввод траты с телефона должен занимать секунд десять, а главный экран должен за пять секунд отвечать на вопрос «сколько мы уже потратили и сколько осталось».

**Основной сценарий — ручной ввод с телефона.** Импорт выписок вторичен, он нужен раз в месяц для сверки. Проектируй интерфейс исходя из этого приоритета, а не наоборот.

### Чему учиться у существующих приложений

Firefly III — самый функциональный self-hosted менеджер финансов, но его же пользователи жалуются, что дашборд заваливает графиками и цифрами до состояния микроскопа. Actual Budget проигрывает по возможностям, но его открывают каждый день, потому что он быстрый и не перегружен. **Мы делаем второе.** Один экран, пять-шесть блоков, каждый отвечает на конкретный вопрос. Если график не меняет ничьё поведение — его нет.

Что стоит взять:
- прогресс-бары по категориям вместо таблиц с числами — визуальный прогресс мотивирует;
- движок правил категоризации (подстрока в описании → категория), он реально экономит время на импорте;
- очередь «неразобранного» вместо тихой автокатегоризации в «Прочее».

Чего не брать: двойную запись, мультивалютность, счета/активы/обязательства, бюджеты-конверты, повторяющиеся транзакции. Всё это — следующая жизнь проекта, не эта.

## 2. Стек и ограничения

- **Next.js (App Router) + React + TypeScript**, строгий режим TS.
- **Tailwind + shadcn/ui.** Только базовые компоненты: `card`, `button`, `input`, `select`, `dialog`, `sheet`, `table`, `tabs`, `badge`, `progress`, `calendar`, `popover`, `form`, `sonner`, `chart`.
- **Графики — recharts** через обёртку `chart` из shadcn, никакой второй графической библиотеки.
- **PostgreSQL 16 в докере**, доступ через **Drizzle ORM** + `drizzle-kit` для миграций.
- **Валидация — Zod**, одна схема на сущность, переиспользуется и на клиенте (react-hook-form), и на сервере. Никакого дублирования типов руками.
- Мутации — **server actions**, чтение — серверные компоненты. Route handlers только там, где нужен настоящий HTTP (загрузка файла).
- **PWA**: манифест, иконки, `display: standalone`. Приложение должно ставиться на домашний экран телефона. Оффлайн-режим не нужен.

Явные запреты, чтобы не разносило:
- никакого стейт-менеджера (Redux, Zustand, Jotai) — хватит серверных компонентов и `useState`;
- никакого react-query;
- никаких абстракций «на будущее»: репозиториев поверх Drizzle, слоя сервисов, DI-контейнеров, фабрик;
- никаких микросервисов, очередей, воркеров, редиса.

Считай, что каждая лишняя движущаяся часть — это будущий вечер отладки вместо ужина.

## 3. Инфраструктура

`docker-compose.yml` в корне, два сервиса:
- `db` — postgres:16-alpine, именованный volume, healthcheck;
- `app` — Next.js в standalone-сборке, multi-stage Dockerfile, зависит от healthy `db`.

Плюс `docker-compose.dev.yml` для локальной разработки: поднимается только `db`, приложение крутится через `next dev` на хосте.

Всё конфигурируется через переменные окружения: `DATABASE_URL`, `AUTH_SECRET`, `APP_CURRENCY` (по умолчанию `€`), `APP_LOCALE` (по умолчанию `ru-RU`). Положи `.env.example` с комментариями.

Скрипт `scripts/backup.sh`: `pg_dump` в файл с датой в имени, ротация 30 дней. В README — строчка для крона и **инструкция как восстановиться из бэкапа**. Год истории трат восстановить неоткуда, если volume снесётся.

Сидирование: `pnpm db:seed` создаёт двух пользователей из env, дефолтный список категорий с лимитами и набор способов оплаты.

## 4. Модель данных

```
users            id, email, password_hash, display_name, created_at
categories       id, name, kind ('expense'|'income'), monthly_limit numeric(12,2) nullable,
                 color, sort_order, archived_at nullable
payment_methods  id, name, archived_at nullable
transactions     id, occurred_on date, kind ('expense'|'income'),
                 amount numeric(12,2) (всегда положительное),
                 category_id, paid_by_user_id, scope ('shared'|'personal'),
                 payment_method_id nullable, note text nullable,
                 import_batch_id nullable, fingerprint text unique nullable,
                 created_by_user_id, created_at, updated_at
import_batches   id, source ('csv'|'txt'), original_filename, uploaded_by_user_id,
                 row_count, imported_count, skipped_count, created_at
category_rules   id, match_type ('contains'|'regex'), pattern text,
                 category_id, scope nullable, priority int
goals            id, title, target_amount, saved_amount, deadline date nullable,
                 archived_at nullable
settings         key, value  (одна строка на настройку: доля партнёра в общих расходах и т.п.)
```

Важные решения, не отходи от них:
- **`amount` — только `numeric`, никогда `float`.** Направление денег определяет `kind`, а не знак.
- **`fingerprint`** — sha256 от `(occurred_on, amount, kind, нормализованное описание, payment_method)`. Уникальный индекс. Это делает импорт идемпотентным: выгружай с любым нахлёстом по датам, дубли просто не запишутся.
- Категории и способы оплаты **архивируются, не удаляются** — иначе история ломается.
- Индексы: `(occurred_on)`, `(category_id, occurred_on)`, `(kind, occurred_on)`.

## 5. Аутентификация

Auth.js (NextAuth) с credentials-провайдером, пароли через argon2 или bcrypt. Ровно два пользователя, создаются сидом, **регистрации в приложении нет**. Middleware закрывает всё, кроме `/login`.

Ролей нет, оба пользователя равны и видят все данные, включая личные траты друг друга. Это осознанное решение: приложение для пары, которая ведёт бюджет вместе, а не для соседей по квартире.

## 6. Ввод данных

### 6.1 Ручной — главный сценарий

Кнопка «Добавить трату» видна с любого экрана (плавающая на мобильном, в шапке на десктопе). Открывает `Sheet` снизу на мобильном, `Dialog` на десктопе.

Форма: сумма (автофокус, цифровая клавиатура), категория, дата (по умолчанию сегодня), «чьё» (общее/личное), кто платил (по умолчанию текущий пользователь), способ оплаты, комментарий. Доход добавляется той же формой через переключатель сверху.

Требования к скорости: цель — **три касания и ввод суммы**. Значит, поля с разумными умолчаниями, категории — сеткой крупных кнопок с самыми частыми наверху (сортировка по частоте использования за последние 30 дней), а не выпадающим списком на двадцать пунктов. После сохранения — тост с кнопкой «Отменить» и форма остаётся открытой для следующей траты.

### 6.2 Импорт CSV / TXT

Страница `/import`, три шага в одном экране:

1. **Загрузка файла.** Drag-and-drop, лимит 5 МБ. Определяем кодировку (`windows-1251` встречается чаще, чем хотелось бы) и разделитель автоматически, но даём переопределить руками.
2. **Сопоставление колонок.** Показываем первые 10 строк файла и селекты «колонка файла → поле транзакции». Обязательны дата, сумма, описание. Даём сохранить сопоставление как профиль под именем банка, чтобы в следующий раз оно подтянулось само.
3. **Предпросмотр и подтверждение.** Таблица разобранных строк с проставленными по правилам категориями. Дубли по `fingerprint` помечены и по умолчанию выключены. Строки без категории подсвечены — их можно разметить прямо здесь, и заодно создать правило «запомнить для этого мерчанта». Внизу: сколько будет создано, сколько пропущено. Импорт выполняется одной транзакцией БД.

Отдельно:
- **TXT-парсер держи изолированным** в `lib/import/parsers/`, с интерфейсом `parse(buffer, options): ParsedRow[]` и юнит-тестами на реальных фикстурах. Формат выписок меняется, менять надо будет один файл.
- Батч импорта **можно откатить целиком** — кнопка в истории импортов. Это страховка от кривого сопоставления колонок.
- Переводы между своими счетами помечаются как `kind: 'transfer'`… **нет, не усложняй**: просто дай возможность исключить строку при импорте. Если понадобится — добавим позже.

## 7. Главная страница — дашборд

Сверху переключатель месяца (стрелки влево-вправо + текущий месяц по центру, клик открывает календарь). Всё ниже пересчитывается под выбранный месяц.

Блоки в этом порядке:

**1. Итог месяца.** Три числа в ряд, крупно: доходы, расходы, остаток. Остаток — самое крупное, зелёный при плюсе, красный при минусе. Рядом мелким — норма сбережений в процентах и дельта к прошлому месяцу («на 12 % меньше, чем в июле»). Сравнение с прошлым месяцем важнее абсолютного числа: оно показывает направление.

**2. Кто кому должен.** Одна строка простым языком: «Ваня переводит Ане 142,50 €» или «Всё поровну». Считается только по расходам со `scope: 'shared'`: сумма общих расходов × доля каждого минус то, что каждый фактически оплатил. Доля берётся из настроек, по умолчанию 50/50. Под строкой — раскрывающийся расчёт, чтобы можно было проверить арифметику.

**3. Категории: факт против лимита.** Список категорий расходов, у каждой прогресс-бар: потрачено / лимит, число и процент. Сортировка по проценту израсходованного, а не по алфавиту — сверху то, что горит. Цвет: обычный до 85 %, янтарный 85–100 %, красный выше. Категории без лимита — в конце, без бара, просто суммой. Клик по категории ведёт в историю с уже наложенным фильтром.

**4. Расходы по дням месяца.** Столбчатый график, ось X — дни. Поверх — тонкая линия накопительного итога и горизонтальная пунктирная линия общего лимита на месяц (сумма лимитов категорий). Сразу видно, идём мы в график или нет.

**5. Структура расходов.** Donut-чарт по категориям, в центре — общая сумма. Максимум 7 сегментов, остальное схлопывается в «Прочее» с возможностью развернуть.

**6. Последние операции.** 8–10 строк, компактно, с кнопкой «Вся история». Это и есть ответ на твой вопрос — отдельная вкладка истории нужна, но её огрызок должен жить на главной, потому что «а что я вчера купил» — второй по частоте вопрос после «сколько осталось».

**Пустые состояния обязательны для каждого блока.** Не «нет данных», а действие: «Ещё ни одной траты в этом месяце. Добавить первую?»

## 8. Остальные страницы

**`/history`** — таблица всех операций. Фильтры: период, категория (мультивыбор), кто платил, общее/личное, способ оплаты, поиск по комментарию. Фильтры живут в URL, чтобы ссылку можно было кинуть друг другу. Сортировка по дате и сумме. Пагинация или бесконечная прокрутка — на твой выбор, но серверная. Строка редактируется инлайн или в шите, удаление с подтверждением. Внизу — сумма по текущему фильтру, это неожиданно полезная вещь. Экспорт отфильтрованного в CSV.

**`/goals`** — накопительные цели: сколько нужно, сколько отложено, прогресс-бар, срок, «откладывать в месяц, чтобы успеть». Простой CRUD.

**`/settings`** — категории и лимиты (drag-and-drop сортировка, цвет, архивирование), способы оплаты, доля каждого в общих расходах, правила категоризации, история импортов с откатом, смена пароля.

## 9. Визуальная часть

shadcn задаёт базу, но не превращай это в очередной админ-дашборд из шаблона.

- **Спокойный нейтральный интерфейс, цвет — только для смысла.** Зелёный = доход и «в рамках лимита», красный = перерасход, янтарный = близко к лимиту. Категории получают свои цвета только внутри donut-чарта и нигде больше. Никаких градиентных заливок и цветных карточек ради красоты.
- **Иерархия за счёт размера, а не рамок.** Не заворачивай каждый блок в одинаковую `Card` с одинаковым радиусом и тенью — это главный признак сгенерированного шаблона. Итог месяца живёт без карточки, крупным типом прямо на фоне; в карточках — только списки и графики.
- **Цифры — табличными цифрами** (`font-variant-numeric: tabular-nums`), иначе колонки сумм скачут. Суммы форматируются через `Intl.NumberFormat` с локалью из env, а не руками.
- **Мобильный — первичный**, десктоп получает более широкую сетку. Проверяй на ширине 380px: если там блок ломается, он не готов.
- Анимации только в ответ на действие пользователя: открытие шита, обновление прогресс-бара после сохранения. Никаких появлений блоков при скролле.
- Тёмная тема — через нативный `next-themes` + переменные shadcn, без ручных `dark:` на каждом элементе.

Копирайтинг: обычный человеческий русский, предложениями. Кнопка говорит, что произойдёт («Сохранить трату», не «Отправить»). Ошибки объясняют, что делать дальше.

## 10. Качество

- Все денежные вычисления — на стороне БД (`SUM`, `GROUP BY`), а не в JS перебором массивов. Дашборд должен быть 3–4 запроса, а не тридцать.
- Юнит-тесты на то, что реально ломается: парсеры импорта, расчёт `fingerprint`, расчёт «кто кому должен» (включая крайние случаи: ноль общих расходов, всё оплатил один, доля не 50/50).
- Один E2E-сценарий на Playwright: логин → добавил трату → она видна на дашборде и в истории.
- Никаких `any` и `@ts-ignore`. Ошибки server actions возвращаются типизированным результатом, а не бросаются в пустоту.
- README: как поднять локально, как задеплоить, как забэкапиться, как восстановиться.

## 11. Порядок работы

Предложи разбиение примерно такого вида и **дождись подтверждения перед каждым этапом**:

1. Каркас: docker-compose, схема Drizzle, миграции, сид, авторизация, пустой лейаут с навигацией.
2. Ручной ввод и история: CRUD транзакций, фильтры, форма быстрого добавления. **На этом этапе приложением уже можно пользоваться каждый день** — дальше идёт улучшение, а не достройка.
3. Дашборд: агрегации в БД, блоки 1–3 (итог, взаиморасчёты, категории).
4. Графики: блоки 4–6.
5. Импорт CSV, профили сопоставления, правила категоризации, откат батча.
6. TXT-парсер, цели, настройки, PWA-манифест, бэкапы, деплой.

Не начинай следующий этап, пока предыдущий не запускается и не проверен руками.
